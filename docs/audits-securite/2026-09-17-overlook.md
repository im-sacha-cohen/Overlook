# Audit de sécurité — Overlook (dépôt complet)

**Date** : 2026-09-17
**Périmètre** : tout le dépôt (`src/app/api/**`, `src/lib/**`, composants client, configuration Docker/Next, dépendances).
**Stack** : Next.js 16.3.3 (App Router, route handlers), React 19, better-sqlite3 (métadonnées + connexions SQLite), pg, mysql2, ssh2. Pas d'authentification applicative (choix documenté dans le README).

**Couvert** : authentification/exposition, API & web (CSRF, DNS rebinding, CORS, XSS), injections SQL, garde-fous « lecture seule » et « prod », accès fichiers via SQLite, cryptographie (secrets au repos, exports chiffrés), tunnel SSH/TLS, télémétrie, journal, dépendances (`npm audit` : 0 vulnérabilité).
**Non couvert** : IA (aucun usage de LLM), site `landing-static/` (HTML statique), infrastructure de déploiement réelle.

Les tests dynamiques ont été faits sur des bases jetables (fichier SQLite dans un dossier temporaire, conteneurs Postgres/MySQL de dev) ; tout a été supprimé ensuite.

---

## Résumé exécutif

| Gravité | Nombre |
|---|---|
| Critique | 2 |
| Élevée | 3 |
| Moyenne | 4 |
| Faible | 5 |

Overlook n'a pas de connexion utilisateur : **quiconque atteint le port de l'application a les pleins pouvoirs** sur toutes les bases enregistrées, y compris la récupération de leurs mots de passe. Or l'application écoute par défaut sur toutes les interfaces réseau (la commande Docker du README comprise), et elle ne vérifie pas le nom de domaine utilisé pour l'appeler, ce qui permet à un simple site web ouvert dans le navigateur de la piloter à distance. Ce sont les deux risques dominants.

Viennent ensuite un contournement du mode « lecture seule » de la console SQL (qui permet d'écrire en prod sans la confirmation prévue), l'accès à n'importe quel fichier SQLite de la machine, et la télémétrie Microsoft Clarity active par défaut sur des écrans qui affichent des données de base non masquées.

Ce qui est sain : les requêtes applicatives sont paramétrées et les identifiants validés, aucune faille XSS trouvée, le chiffrement des secrets (AES-256-GCM, IV aléatoire) et des exports (scrypt borné) est correct, et les secrets ne sont jamais renvoyés au navigateur.

## Constats Critique

### [Critique] Aucune authentification et écoute sur toutes les interfaces réseau

**Catégorie** : Auth / Infra
**Référence** : CWE-306 (Missing Authentication for Critical Function), OWASP API2:2023
**Statut** : confirmé

**Où**
- Aucun `src/proxy.ts` ni contrôle d'accès dans les route handlers (`src/app/api/**`).
- `README.md:64` : `docker run -d -p 3000:3000 ...` publie le port sur toutes les interfaces.
- `lsof` pendant l'audit : `TCP *:3000 (LISTEN)` (Docker) et `TCP *:60229 (LISTEN)` (`next dev`).

**Scénario d'exploitation**
1. Une personne sur le même réseau (Wi-Fi de coworking, réseau d'entreprise, VPN) trouve le port 3000 ouvert sur la machine.
2. `GET http://<ip>:3000/api/connections` liste toutes les connexions et leurs identifiants.
3. `POST /api/connections/bundle/export` avec `{"ids":[...],"includePasswords":true,"passphrase":"<choisie par l'attaquant>"}` renvoie les mots de passe, clés SSH et certificats chiffrés **avec la phrase de passe de l'attaquant**, qui les déchiffre ensuite hors ligne.
4. Autre voie : `POST /api/connections/<id>/query` exécute n'importe quel SQL sur n'importe quelle base.

Vérification : depuis une autre machine du réseau, `curl http://<ip>:3000/api/connections` doit répondre 200.

**Impact réel pour ce projet**
Vol des identifiants de toutes les bases enregistrées (dont les connexions `PROD`), lecture et destruction des données, rebond vers les réseaux joignables par tunnel SSH. Le README parle d'« environnement de confiance », mais la commande d'installation qu'il donne expose l'outil au réseau local.

**Correctif**
1. **Rapide** : documenter et utiliser `-p 127.0.0.1:3000:3000` pour Docker, et lier `next dev`/`next start` à `127.0.0.1` (`-H 127.0.0.1`) dans les scripts.
2. **Recommandé** : une authentification optionnelle mais activée dès qu'une variable est définie (ex. `OVERLOOK_PASSWORD`) : `src/proxy.ts` qui exige un cookie de session `HttpOnly; SameSite=Strict` posé après saisie du mot de passe (comparaison à temps constant), avec avertissement au démarrage si l'app écoute hors de `127.0.0.1` sans mot de passe.
3. **Structurant** : exiger la phrase de passe maîtresse (ou une ré-authentification) pour l'export de connexions avec mots de passe.

### [Critique] Pas de contrôle du Host : pilotage à distance par DNS rebinding

**Catégorie** : Web
**Référence** : CWE-350 (Reliance on Reverse DNS Resolution), CWE-346 (Origin Validation Error)
**Statut** : confirmé

**Où**
Aucune vérification de l'en-tête `Host` ni de l'`Origin` sur les routes `src/app/api/**`. Test : `curl -H 'Host: attacker.example:60229' http://localhost:60229/api/connections` → **200** avec la liste des connexions.

**Scénario d'exploitation**
1. L'utilisateur fait tourner Overlook en local (`localhost:3000`), même lié à `127.0.0.1`.
2. Il ouvre une page piégée sur un domaine de l'attaquant dont le DNS pointe d'abord vers le serveur de l'attaquant, puis vers `127.0.0.1` (DNS rebinding).
3. Le navigateur considère alors les appels vers `http://attaquant.example:3000/api/...` comme de même origine : la page lit `/api/connections`, puis appelle l'export de connexions avec mots de passe comme au constat précédent, et renvoie le tout à l'attaquant.

Vérification : l'appel avec un `Host` étranger ci-dessus doit être refusé (403) après correction.

**Impact réel pour ce projet**
Même impact que l'absence d'authentification, **à distance par Internet**, pour tout utilisateur qui ouvre un site malveillant pendant qu'Overlook tourne, y compris sur un poste bien configuré en local uniquement.

**Correctif**
`src/proxy.ts` (le « middleware » de Next 16, voir `node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md`) appliqué à `/api/:path*` :
- refuser toute requête dont le `Host` n'est pas dans une liste blanche (`localhost`, `127.0.0.1`, `[::1]` + variable `OVERLOOK_ALLOWED_HOSTS` pour un déploiement derrière un domaine) ;
- pour les méthodes non-GET, refuser si l'en-tête `Origin` est présent et ne correspond pas au `Host` autorisé.

L'authentification du constat précédent protège aussi contre ce scénario, mais le contrôle du Host reste utile même avec elle.

## Constats Élevée

### [Élevée] Le mode « lecture seule » et la confirmation prod se contournent (écriture sans garde-fou)

**Catégorie** : Base de données / Logique métier
**Référence** : CWE-863 (Incorrect Authorization), CWE-693 (Protection Mechanism Failure)
**Statut** : confirmé sur SQLite, PostgreSQL et MySQL

**Où**
`src/lib/api/sql-guard.ts:3`

```ts
const READ_ONLY_PREFIXES = ["select", "with", "explain", "show", "pragma", "describe"];
export function isReadOnlyStatement(sql: string): boolean {
  const trimmed = sql.trim().toLowerCase();
  return READ_ONLY_PREFIXES.some((p) => trimmed.startsWith(p));
}
```

`src/app/api/connections/[id]/query/route.ts` : si la requête est jugée « lecture seule », ni `allowWrite`, ni la confirmation prod, ni le journal ne s'appliquent. `src/lib/db/mysql.ts` ouvre le pool avec `multipleStatements: true` ; `pg` accepte plusieurs instructions sans paramètres.

**Scénario d'exploitation**
Sans cocher « Autoriser les requêtes d'écriture » et sans taper le nom d'une connexion `PROD` :
- `WITH x AS (SELECT 1) DELETE FROM t` (SQLite) → lignes supprimées ;
- `WITH d AS (DELETE FROM t RETURNING id) SELECT count(*) FROM d` (PostgreSQL) → lignes supprimées ;
- `SELECT 1; DROP TABLE t` (MySQL et PostgreSQL) → table supprimée, puis une erreur s'affiche.

Tous ces cas ont été reproduits sur des tables de test.

**Impact réel pour ce projet**
La protection phare du produit (« ne jamais modifier la prod par erreur ») ne tient pas : une requête collée d'ailleurs, ou un script, peut modifier ou détruire des données de production **sans confirmation et sans trace dans le journal**.

**Correctif**
Ne plus deviner à partir du préfixe ; faire garantir la lecture seule par la base :
- **PostgreSQL** : exécuter dans `BEGIN READ ONLY; …; ROLLBACK` sur un client dédié, en refusant plusieurs instructions (utiliser le protocole étendu, ex. `client.query({ text: sql, values: [] })`, qui n'accepte qu'une instruction).
- **MySQL** : pool dédié à la console avec `multipleStatements: false` et `START TRANSACTION READ ONLY` ; garder `multipleStatements` uniquement pour l'import de script (qui passe déjà par la confirmation).
- **SQLite** : `db.prepare(sql)` refuse déjà plusieurs instructions ; utiliser la propriété `stmt.readonly` de better-sqlite3 pour décider, et refuser `ATTACH`/`DETACH`/`PRAGMA` modifiants.
- Dans tous les cas, journaliser aussi les requêtes considérées en écriture par la base.

### [Élevée] Une connexion SQLite donne accès à n'importe quel fichier SQLite de la machine et crée des fichiers n'importe où

**Catégorie** : Stockage de fichiers / Base de données
**Référence** : CWE-73 (External Control of File Name or Path)
**Statut** : confirmé

**Où**
- `src/lib/db/sqlite.ts` : `new Database(conn.database)` avec un chemin libre (création, modification, brouillon de test de connexion et import de bundle compris).
- `src/app/api/connections/[id]/query/route.ts` → `runRawQuery` accepte `ATTACH DATABASE '<chemin>' AS a`.

**Scénario d'exploitation**
1. Créer une connexion SQLite vers `data/app-metadata.db` : la table `connections` et surtout `journal` (valeurs avant/après des lignes de prod) et `query_history` sont lisibles et modifiables. Testé : lecture réussie.
2. `ATTACH DATABASE '/chemin/au/choix' AS a` crée un fichier à cet emplacement (testé dans un dossier temporaire). Même chose via `POST /api/connections/test` avec un brouillon SQLite, sans connexion enregistrée.
3. Lancé en local (`npm start`/`next dev`), cela ouvre les bases SQLite de l'utilisateur : historique et cookies de navigateurs (Firefox stocke `cookies.sqlite` en clair), bases d'autres applications.

**Impact réel pour ce projet**
Au-delà des bases que l'utilisateur a choisi d'ajouter, quiconque accède à l'app (constats critiques) lit les fichiers SQLite du système (sessions de navigateur, données d'autres apps) et crée ou modifie des fichiers accessibles au processus Node.

**Correctif**
- Restreindre les chemins SQLite à un ou plusieurs dossiers autorisés (variable `OVERLOOK_SQLITE_DIRS`, par défaut le dossier de travail et `./dev`), avec `path.resolve` + vérification du préfixe après résolution des liens symboliques ; refuser `DATA_DIR`.
- Ouvrir en `{ fileMustExist: true }` pour les connexions et le test (la création passe uniquement par « Créer la base »).
- Refuser `ATTACH`/`DETACH` dans la console (voir le constat précédent, `stmt.readonly` ne les bloque pas tous).

### [Élevée] Télémétrie Microsoft Clarity active par défaut sur des écrans qui affichent des données de base non masquées

**Catégorie** : Infra / Confidentialité
**Référence** : CWE-359 (Exposure of Private Personal Information to an Unauthorized Actor)
**Statut** : à vérifier — le mode de masquage configuré sur le projet Clarity `yahgty78gs` (tableau de bord Clarity) détermine si ces textes sont réellement transmis

**Où**
- `src/components/Telemetry.tsx:7` : projet partagé « Overlook OSS » par défaut, chargé dans `src/app/layout.tsx` sur **toutes** les pages de l'app, sauf `NEXT_PUBLIC_DISABLE_TELEMETRY=1`.
- Seuls les vues de table, tableau, calendrier, galerie et le panneau de détail portent `data-clarity-mask`. **Non masqués** : résultats et SQL de la console (`QueryConsole.tsx`), journal avec valeurs avant/après (`JournalPanel.tsx`), comparaison de données (`CompareView.tsx`), aperçu SQL avec valeurs (`WritePreviewBox.tsx`), diagramme et noms de tables, formulaire de connexion (hôte, utilisateur), et l'URL (`?c=…&t=<table>`).

**Scénario d'exploitation**
Une personne qui auto-héberge Overlook sans lire la section Télémétrie ouvre la console SQL sur sa base de prod : les résultats affichés font partie de l'enregistrement de session envoyé à Clarity et visible par quiconque a accès au tableau de bord partagé.

**Impact réel pour ce projet**
Fuite potentielle de données de production (données personnelles de clients, schémas, hôtes internes) vers un tiers et vers le mainteneur du tableau de bord partagé, sans consentement explicite de l'utilisateur ; enjeu RGPD pour les utilisateurs européens.

**Correctif**
- **Recommandé** : télémétrie désactivée par défaut dans l'application (opt-in), ou limitée aux pages de la landing.
- Si elle reste active : poser `data-clarity-mask="true"` sur le conteneur racine du `Workspace` (tout masquer) et configurer le projet Clarity en mode « Strict ».

## Constats Moyenne

### [Moyenne] CSRF : les routes POST acceptent des requêtes « simples » venant d'autres sites

**Catégorie** : Web — **Référence** : CWE-352 — **Statut** : confirmé

Les handlers lisent `request.json()` sans vérifier `Content-Type` ni `Origin`. Une page tierce peut envoyer `fetch(url, { method: "POST", mode: "no-cors", body: JSON })` (en-tête `text/plain`, sans preflight) : testé avec `Origin: https://evil.example`, la connexion est créée. Le site tiers ne lit pas la réponse et ne connaît pas les identifiants des connexions, donc l'impact direct se limite à : créer ou importer des connexions, lancer des tests de connexion vers le réseau interne (sondage de ports à l'aveugle), créer des fichiers SQLite vides n'importe où (via le constat précédent).
**Correctif** : dans `src/proxy.ts`, refuser les méthodes non-GET dont l'`Origin` ne correspond pas au Host autorisé, et exiger `Content-Type: application/json`. Le correctif du DNS rebinding couvre les deux.

### [Moyenne] Clé d'hôte SSH jamais vérifiée (attaque de l'homme du milieu sur le tunnel)

**Catégorie** : Infra — **Référence** : CWE-322 — **Statut** : confirmé

`src/lib/db/sshTunnel.ts` : la configuration `ssh2` n'a pas de `hostVerifier`, donc n'importe quelle clé serveur est acceptée. Quelqu'un en position d'interception (DNS, réseau) se fait passer pour le bastion : il récupère le mot de passe SSH en clair (authentification par mot de passe) et voit ou modifie le trafic vers la base.
**Correctif** : mémoriser l'empreinte de la clé au premier test réussi (TOFU), l'afficher dans le formulaire, et refuser toute clé différente ensuite (option « empreinte attendue » saisissable).

### [Moyenne] La clé de chiffrement est rangée à côté des données chiffrées

**Catégorie** : Cryptographie — **Référence** : CWE-320 — **Statut** : confirmé

Sans `APP_SECRET`, la clé est dans `data/secret.key`, dans le même dossier ou volume Docker que `app-metadata.db` (`src/lib/store/crypto.ts`). Une sauvegarde ou une copie du volume contient donc de quoi déchiffrer tous les mots de passe, clés SSH et certificats : le chiffrement au repos ne protège pas dans ce cas courant.
**Correctif** : avertissement au démarrage (et dans Paramètres) quand `APP_SECRET` n'est pas défini ; dans la doc Docker, passer `APP_SECRET` par variable ou secret Docker plutôt que de le laisser générer dans le volume.

### [Moyenne] Copies de données de production en clair dans la base de métadonnées

**Catégorie** : Base de données — **Référence** : CWE-312 — **Statut** : confirmé

`journal.details` garde jusqu'à 500 lignes « avant » par modification (lignes supprimées entières), `journal.sql` et `query_history.sql` gardent le SQL avec ses valeurs, pendant 90 jours, en clair dans `data/app-metadata.db`. Quiconque obtient ce fichier (sauvegarde, constat SQLite ci-dessus) récupère des données de prod hors de la base d'origine.
**Correctif** : chiffrer `details` et `sql` avec la même clé que les secrets (AES-GCM déjà en place), et proposer une rétention plus courte pour les connexions `PROD`.

## Annexe — Faible / hardening

1. **Injection de formules dans l'export CSV du journal** (CWE-1236) : `src/app/api/journal/export/route.ts` n'échappe pas les cellules commençant par `=`, `+`, `-`, `@` (SQL, noms de tables, auteur). Préfixer ces cellules par `'`.
2. **Auteur et IP du journal falsifiables** (CWE-348) : `X-Overlook-User` est déclaratif et l'IP vient de `X-Forwarded-For` sans proxy de confiance. Le signaler dans l'interface (« déclaré ») et n'utiliser `X-Forwarded-For` que derrière un proxy configuré.
3. **En-têtes de sécurité absents** : pas de `X-Frame-Options`/`frame-ancestors` (clic détourné via une iframe, par exemple sur les dialogues de confirmation), ni `X-Content-Type-Options` ou `Referrer-Policy`. À ajouter dans `next.config.ts` (`headers()`).
4. **Consommation de ressources non bornée** : `limit` non plafonné sur `GET …/rows`, pas de taille maximale sur les imports CSV, SQL et bundle, comparaison chargeant jusqu'à 40 000 lignes en mémoire. Plafonner `limit` (ex. 1 000) et la taille des corps de requête.
5. **Garde-fou prod incomplet côté serveur** : insertion, modification de cellule, import CSV, ajout ou renommage de colonne, création de table et collage de cellules ne demandent pas `confirm` côté API. Acceptable si le garde-fou est vu comme une protection contre les erreurs d'interface et non comme un contrôle d'accès ; à documenter ou à étendre.
